**数据面（三个握手文件）与"谁写谁读"**：

| 文件 | 方向 | 内容 | 写入时机 |
|------|------|------|----------|
| `log/otp_want.txt` | 发起端 → 守望 | `邮箱｜runid` | 提交邮箱表单后立即写 |
| `log/grok_otp_<runid>.txt` | 守望 → 发起端 | 验证码本体（如 `726-480`） | 提取命中后 |
| `log/watch_run.txt` | 守望 → 状态条/审计 | 状态行日志（追加） | 全程 |

**为什么这套架构长这样（思路）**：

1. **跨进程跨 App**：发起端跑在 AutoJs6（另一个 App 的 WebView 环境），守望跑在 Termux（不同 UID）。
   Android 沙箱下最便宜的互通方式 = **共享存储文件**（无 socket、无端口、无权限博弈），且天然留痕可审计。
2. **职责分离**：发起端只关心"网页怎么填"，守望只关心"邮件怎么取"。
   换邮箱源（QQ→Outlook→临时邮箱 API）不动发起端；换页面不动守望（见 [otp-fast-extract 的框架文档](https://github.com/daodaoyu123/otp-fast-extract)）。
3. **runid 隔离**：注册是连续多轮跑的。`runid = String(Date.now())` 把 want / code / 状态三处全部按轮隔离——
   防止"上一轮的旧码/旧超时"污染本轮（实测踩过：状态条显示上一轮的超时）。


**思路**：三个数字（10 / 1 / 5）是整套"快"的核心参数：
- `PUSH_WAIT=1`：QQ 经常**不推送**，空挂 10 秒/次会把每轮拖成 10 秒+；1 秒是"给它一个推送机会、不浪费"的平衡点。
- `SCAN=10`：QQ 垃圾箱里验证码永远在最前面几封，扫 10 封足够且快。
- `IDLE_WAIT=5`：空闲时也要"每 5 秒醒一次看有没有新目标"，否则新注册要干等。

### 3.2 连接与能力探测（含 QQ 的坑）

```python
def connect():
    password = open(SECRET, encoding="utf-8").read().strip()
    client = imaplib.IMAP4_SSL("imap.qq.com", 993, timeout=30)
    client.login(USER, password)
    client.capability()          # ← 关键：登录之后才读能力
    return client

def supports_idle(client):
    return b"IDLE" in client.capabilities or "IDLE" in client.capabilities
```

**坑（已在代码注释里固化）**：QQ 的 `IDLE` 能力**只在登录之后**才出现在 `capabilities` 里。
登录前判断会误判成"不支持 IDLE"，从而退化成低效轮询。

**坑 2（Python 版本，2026-09-26 实测）**：`client.idle()` 是 **Python 3.14** 才加进标准库 `imaplib` 的。
在 3.13 上跑守望会直接抛 `AttributeError: Unknown IMAP4 command: 'idle'`（tmux 会话随即消失）。
现场版处置（1 行，且不损失 3.14 的推送能力）：

```python
def supports_idle(client):
    # [3.13 兼容] 3.14 起标准库才有 idle()；无该方法则降级走 noop 短轮询
    if not hasattr(client, "idle"):
        return False
    return b"IDLE" in client.capabilities or "IDLE" in client.capabilities
```

降级后走 `wait_push` 的 noop 分支（`sleep(1)` + `noop()`），再靠主动重扫兜底 —— 实测单轮
2.7~3.3 秒、功能正常，只是失去"推送即时"这一层。

**坑**：QQ 对垃圾箱有个脾气——**不 `close` 直接 `select` 不给刷新**，新信"看不见"。
所以每个搜索周期都"重开垃圾箱"，这是刻意为之，不是多余。

### 3.4 提取与归属判定（防串轮的核心）

```python
def code_from_header(raw, target):
    """从信头里判归属 + 提码：收件人（To 或 Delivered-To）必须等于当前邮箱。"""
    parsed = email.message_from_bytes(raw)
    blob = (header_text(parsed.get("To")) + " " +
            header_text(parsed.get("Delivered-To"))).lower()
    if target.lower() not in blob:
        return None                                    # ← 不是当前邮箱：直接丢
    match = re.search(r"(\d{3}-\d{3})", header_text(parsed.get("Subject")))
    return match.group(1) if match else None
```

**思路（三道防线之一）**：垃圾箱里可能有**别人/上一轮**的验证码（同一域名前缀很像）。
判定必须"收件地址 == 当前目标邮箱"才算数；`To` 和 `Delivered-To` 都扫（转发链路下两者可能只有一个是原始地址）。
信头可能是 `=?utf-8?B?...?=` 编码，先 `decode_header` 再正则。

**为什么不用 IMAP 的 `TO` 搜索**（实测坑）：QQ 的搜索索引会把**上一封旧验证码**立刻判成命中
（旧信也在 Junk、收件人同域），新邮件反而要等几十秒才进索引。改成"发 `fetch` 扫最新 N 封 + 逐封判收件人"
后，一轮 1 秒出头、确定性返回。

### 3.5 双路等信（1 秒推送窗 + 主动重扫）

```python
def wait_push(client, seconds):
    """挂住垃圾箱等新信。返回 exists / timeout / noop / denied / error。"""
    if not supports_idle(client):          # ← 3.13 及以下总走这里（见 3.2 坑 2）
        time.sleep(seconds)
        try:
            client.noop()
        except imaplib.IMAP4.error:
            return "error"
        return "noop"
    got = "timeout"
    try:
        with client.idle(duration=seconds) as idler:
            for typ, data in idler:
                if typ == "EXISTS": got = "exists"; break
                if typ == "RECENT" and data not in (None, b"0", "0"):
                    got = "exists"; break
    except (imaplib.IMAP4.abort, OSError, TimeoutError):
        return "error"
    except imaplib.IMAP4.error:
        return "denied"
    return got
```

```python
def take_code(client, target, seen, deadline):
    """先等 1 秒推送；没有就重开垃圾箱主动查。返回 (码, UID)。"""
    tries = 0
    while time.time() < deadline:
        if changed(target):                    # ← 检查点①：目标换了就弃
            print("目标已更换, 放弃: %s" % target); return None, None
        tries += 1
        t_try = time.time()
        if not ensure_junk(client):
            raise imaplib.IMAP4.abort("junk not open")
        event = wait_push(client, min(PUSH_WAIT, max(0.2, deadline - time.time())))
        if event == "error":
            raise imaplib.IMAP4.abort("idle/noop failed")
        if event == "exists":                  # 路A：推送命中 → 精确读新 UID
            fresh = new_uids(client, seen)
            for one in fresh:
                code = fetch_uid(client, one, target)
                if code:
                    print("  第%d次 %.1fs 推送命中" % (tries, time.time() - t_try))
                    return code, one
        code, uid = find_code(client, target)  # 路B：不管推没推，都主动重扫
        if uid: seen.add(uid)
        print("  第%d次 %.1fs %s" % (tries, time.time() - t_try, "命中" if code else "无"))
        if code: return code, uid
    return None, None
```

**思路**：路 A（IDLE 推送）和路 B（主动重扫）**每个周期都跑**，不互斥——
推送来了走精确路径（快），没来立即重扫（兜底），单周期 ≈1 秒。日志的 `第N次 X.Xs 命中/无` 就是心跳。

```python
def delete_uid(client, uid):
    """按 UID 删信（防重复匹配）。删不了不影响已写入的码。"""
    if not uid: return
    try:
        client.uid("STORE", uid, "+FLAGS", "\\Deleted")
        client.expunge()
        print("已删除验证码邮件", flush=True)
    except imaplib.IMAP4.error as exc:
        print("删除失败(不影响取码): %s" % exc, flush=True)
```

**思路**：`seen` 集合避免对同一封反复 FETCH；取到后**先写文件、再删邮件**——
删除失败只记一行日志，码已经安全落盘（顺序不能反）。

```python
def main():

    print("等待接收验证码", flush=True)

    open_junk(client)
    seen_key = ""; seen = set()
    while True:
        content = read_want()
        # —— 空闲：挂 5 秒，只为尽快发现 otp_want.txt 换了新邮箱 ——
        if not content or content == seen_key:
            if ensure_junk(client):
                event = wait_push(client, IDLE_WAIT)
                if event == "exists": new_uids(client, seen)
            else:
                time.sleep(1)
            continue
        # —— 新目标 ——
        seen_key = content
        target, runid = [x.strip() for x in content.split("|", 1)]
        out = REG + "/log/grok_otp_" + runid + ".txt"
        if already_written(out):               # 幂等：本轮已有码就跳过
            print("已写入, 不再提取: %s" % target, flush=True)
            print("等待接收验证码", flush=True); continue
        print("提取验证码: %s (runid=%s)" % (target, runid), flush=True)
        deadline = time.time() + 180
        try:
            code, uid = take_code(client, target, seen, deadline)
        except imaplib.IMAP4.abort:
            client = connect()                 # 连接坏了：重连
        if changed(target): continue           # 检查点②
        if not code:
            code, uid = find_code(client, target)   # 断线补查一次
        if changed(target): continue           # 检查点③
        if not code:
            print("超时未收到: %s" % target, flush=True)
            print("等待接收验证码", flush=True); continue
        print("提取成功: %s" % code, flush=True)
        # ← 落盘（现场版为原子写：tmp + rename，防发起端 100ms 一跳读到半截码）
        _tmp = out + ".tmp"
        with open(_tmp, "w", encoding="utf-8") as _f:
            _f.write(code)
        os.replace(_tmp, out)
        print("写入验证码: %s" % code, flush=True)
        print("CODE_WRITTEN %s -> %s" % (code, out), flush=True)
        delete_uid(client, uid)                # ← 删信
        if client.state != "SELECTED": open_junk(client)
        print("等待接收验证码", flush=True)
```

### 3.8 可靠性小结（守望端）

| 场景 | 处理 |
|------|------|
| 连接坏（IDLE/noop 失败） | 重连，丢当前轮的一次尝试 |
| 取码中途断线 | 重连后**补查一次**（断线期间到的信不放过） |
| 目标被换（换邮箱） | 三个检查点发现即弃，不空耗 180 秒 |
| 本轮已有码 | `already_written` 幂等跳过 |
| 重复触发 | `seen` 集合 + 已删信双重防重 |
| 空转检测 | 连续 `0.0s 无` 返回=连接空转坏 → 重启守望（见排错表） |

**思路**：**先写再等**。如果先等再写，存在"信已到邮箱、但守望不知道收哪个邮箱"的窗口期。
`RUNID = String(Date.now())`，与 want、code 文件名三处一致。

### 4.2 等码（100ms 轮询）

```javascript
// ---- 文件桥: 等 Termux 侧的守望把验证码写进来 ----
function codeFromFile() {
    var f = REG + "/log/grok_otp_" + RUNID + ".txt";
    var w0 = Date.now();
    while (Date.now() - w0 < 300000) {                 // 上限 5 分钟
        try { if (files.exists(f)) {
            var c = String(files.read(f)).trim();
            if (c) return c;
        } } catch (e) {}
        sleep(100);                                    // ← 100ms 一跳
    }
    return null;
}
```

**思路**：本地文件轮询足够便宜，**跳得越密回填越早**（实测落盘→读到 ≤0.1s）。
5 分钟兜底 > 守望单轮 180s，保证"守望先超时、发起端自己判断"的顺序不颠倒。

### 4.3 回填（本文重点：WebView 填码的三个技术点）

```javascript
function fillCode(code) {
    var flat = code.replace(/-/g, "");        // ① 拍平：726-480 → 726480
    return runJsSync("(function(code){try{" +
        "var ins=document.querySelectorAll('input');var vis=[];" +
        "for(var i=0;i<ins.length;i++){" +
        "  var t=(ins[i].type||'').toLowerCase();" +
        "  if(t==='email'||t==='password'||t==='hidden'||t==='checkbox')continue;" +  // ② 过滤非码框
        "  var r=ins[i].getBoundingClientRect();" +
        "  if(r.width<=0||r.height<=0)continue;vis.push(ins[i]);}" +                   //    只看可见的
        "if(vis.length===0)return 'NOBOX';var d;" +
        "var one=vis.filter(function(e){return String(e.maxLength)==='1'||" +
        "  e.getAttribute('maxlength')==='1';});" +
        "if(one.length>=4){" +                                                         // ③ 六格形态
        "  for(var k=0;k<one.length&&k<code.length;k++){" +
        "    d=Object.getOwnPropertyDescriptor(one[k].__proto__,'value');" +          // ④ 原生 setter
        "    d.set.call(one[k],code.charAt(k));" +
        "    one[k].dispatchEvent(new Event('input',{bubbles:true}));}" +             // ⑤ input 事件
        "  return 'FILLED_BOXES_'+one.length;}" +
        "d=Object.getOwnPropertyDescriptor(vis[0].__proto__,'value');" +              // 单框形态
        "d.set.call(vis[0],code);" +
        "vis[0].dispatchEvent(new Event('input',{bubbles:true}));" +
        "return 'FILLED_ONE';}catch(e){return 'E:'+e;}})('" + flat + "')");
}
```

**三个技术点（思路）**：

1. **直接 `el.value = x` 会被 React 吞掉**。注册页是 React 受控组件，值绑定在框架内部。
   必须走**原生 setter**：`Object.getOwnPropertyDescriptor(el.__proto__, 'value').set.call(el, v)`
   ——绕过实例上的受控拦截，再 `dispatchEvent(new Event('input', {bubbles:true}))` 通知框架"用户输了"。
   （邮箱输入 `fillEmail` 用的是同一招。）
2. **两种页面形态都要支持**：`maxLength=1` 且 ≥4 个可见框 = 六格 OTP，逐格填；
   否则填第一个可见输入框。实测本注册页近期都是 `FILLED_ONE`（单框），六格分支是给别家页面留的。
3. **只挑"看得见"的框**：`getBoundingClientRect()` 宽高 >0 才算（隐藏框兜底不会误填）。

**日志证据**（真实）：
```
[4] 验证码: 已获取(长度7)     ← "726-480"，7 个字符（含连字符）
[4] 填码: FILLED_ONE          ← 单框形态，填 726480
```

### 4.4 提交与确认

```javascript
log("[4] 填码: " + fillCode(code));
if (!waitJs("!!document.querySelector('input[type=password]')", 5000, 300)) {
    actByText(["确认邮箱", "确认", "验证", "Continue", "Verify"], "[4]");

```

**思路**：填码后不盲目点按钮——**先等 5 秒看页面有没有自己前进**（出现资料页的 password 框就是过了）；
没前进才去点"确认/Verify"。避免"页面已自动提交，脚本又点一次"造成的重复提交。

### 4.5 状态条（把守望状态注入 WebView 顶层）

```javascript
function watchState() {
    var st = "守望未启动";
    try {
        var s = String(files.read(WATCH_LOG));          // 读 watch_run.txt
        var lines = s.split("\n").filter(function (x) { return x.trim().length > 0; });
        var cur = String(files.read(REG + "/log/otp_want.txt")).trim();
        var runid = cur.indexOf("|") >= 0 ? cur.split("|")[1] : "";
        var seg = [];
        if (runid) {                                    // ★ 只看"本轮 runid 之后"的日志
            for (var k = lines.length - 1; k >= 0; k--) {
                seg.unshift(lines[k]);
                if (lines[k].indexOf(runid) >= 0) break;
            }
        }
        var last = seg.length ? seg[seg.length - 1] : ...;
        st = runid ? "等待接收验证码" : "守望空闲";
        if (last.indexOf("等待接收验证码") >= 0) st = "等待接收验证码";
        var sm = last.match(/第(\d+)次\s*[\d.]+s\s*(?:推送)?(命中|无)/);
        if (... || sm) st = sm ? ("提取验证码 · 第" + sm[1] + "次 · " + sm[2]) : "提取验证码";
        if (last.indexOf("提取成功") >= 0) st = "提取成功" + ...;
        if (last.indexOf("写入验证码") >= 0 || last.indexOf("CODE_WRITTEN") >= 0) st = "写入验证码" + ...;
        if (last.indexOf("超时未收到") >= 0) st = "超时未收到";
    } catch (e) {}
    return st;
}
// 1 秒刷新一次，颜色：红=超时 / 绿=成功路径 / 黄=进行中
threads.start(function () {
    while (true) { paintWatch(watchState()); sleep(1000); }
});
```

**思路（两个重要决定）**：
1. **状态条是原生控件挂在 WebView 顶层**（`ui.layout` 里 frame 的最后一个子节点），
   不随页面跳转/cookie 弹层消失；页面跳 N 次它都在。
2. **状态读取按当前 runid 截断**：从日志尾部往前，**直到遇到本轮 runid 那一行就停**。
   否则上一轮的"超时未收到"会在新一轮刚开始时被误显示（实测踩过这个 bug）。

> **修正记录（2026-09-26）**：定稿版此处的正则匹配不上守望的真实输出 ——
> `/第(\d+)次搜索.*?(命中|无)/` 要求“第N次”后面紧跟 **“搜索”** 二字，
> 而守望实际打印的是 `第1次 1.2s 无`（**没有“搜索”**），于是状态条永远取不到“第N次”，只能退到粗粒度的“提取验证码”。
> 现场已改为 `/第(\d+)次\s*[\d.]+s\s*(?:推送)?(命中|无)/`，实测四种真实日志格式（含“推送命中”）全部命中。

## 5. 设计思路总表（决策 vs 理由）

| 决策 | 替代方案 | 为什么这样 |
|------|----------|------------|
| 共享存储文件桥 | socket / HTTP / 广播 | 跨 App 跨 UID 零权限摩擦；天然可审计；断任何一端可单独重启 |
| runid 三段隔离 | 单一文件 | 连续多轮必须防串轮（want/code/状态三处都带） |
| 收件地址精确匹配 | 只凭标题正则 | 垃圾箱里会有同域旧码；地址匹配是"这是本轮的"硬证据 |
| 1 秒 IDLE 推送窗 + 主动重扫 | 空挂 10 秒/次 | QQ 常不推送；1 秒窗+重扫把单周期压到 ~1s |
| 只扫最新 10 封、新→旧 | 全量/IMAP 搜索 | 搜索索引有"旧码秒命中"假阳性；扫 10 封确定性更强 |
| 提取后删信 | 留着不管 | 防同一封被后续轮次重复匹配 |
| 落盘用（近）原子写 | 裸写 | 发起端 100ms 一跳，防读到半截（参考实现已用 tmp+rename） |
| 发起端 100ms 轮询 | 500ms/1s | 本地文件轮询极便宜，回填延迟直接取决于此 |
| 原生 setter + input 事件 | `el.value=` | React 受控组件会吞直接赋值 |
| 填码后先等 5s 再点按钮 | 填完就点 | 页面可能自动提交，防重复点 |
| 状态条读日志文件 | 与守望 RPC | 跨 App 无法直连；文件即 RPC，顺带可审计 |
| 状态按 runid 过滤 | 读最后一行 | 防上一轮残留污染（踩过） |
| 空闲不退出（挂 5s 探测） | 300s 自杀 | 自杀导致下一轮没人收码（踩过） |

## 6. 故障处理与排错表（验证码段）

| 症状 | 判定 | 处理 |
|------|------|------|
| 状态一直「等待接收验证码」 | want 没写上 / 守望没起 | 看 `otp_want.txt` mtime；`ps`/tmux 看守望进程 |
| 「第N次 X.Xs 无」连续多次且 X 越来越大 | 信还没到（正常） | 等；超过 180s 会显示超时 |
| 「第N次 0.0s 无」连续多次 | IMAP 连接空转坏了 | 重启守望（重新登录） |
| 「超时未收到」但邮箱里有信 | 收件人匹配不过 / 信进了别的箱 | 对比 want 邮箱与信头 To/Delivered-To；**查收件箱**（QQ 偶发把码投收件箱） |
| 填码返回 `NOBOX` | 页面未渲染完 | 等页面加载再填（调用方已有等待逻辑） |
| 填码返回 `E:...` | 页面结构变了 | 看日志里的异常原文，更新 fillCode 的选择器 |
| 提交后页面报"验证码错误" | 串轮/旧码 | 检查 runid 三处一致；检查收件人匹配是否被绕过 |
| `FILLED_BOXES_6` 但没过 | 六格填法不适用该站 | 检查是否应走单框分支 |
| 全部正常但页面不动 | 码对了但没提交 | 看"确认邮箱/Verify"按钮文案是否变了 |

## 7. 与其它注册机实现的源码级对照

> 以下来自对 `grok-register`（AaronL725 系）与 `grok-pure`（纯协议系）源码的通读，
> 详细版见 [otp-fast-extract](https://github.com/daodaoyu123/otp-fast-extract) 的文档。

| 项目/实现 | 取码方式 | 与本文方案的差异 |
|-----------|----------|------------------|
| 本注册机（守望） | QQ 垃圾箱 IMAP，1s 窗口+重扫 | 只扫 Junk 一箱（改进方向：加收件箱双箱） |
| `grok-register/mail_service.py`（DuckMail 源） | 3s 轮询 API，180s 超时 | 一次性邮箱无垃圾箱概念；先校验收件人 |
| 同上 `outlook_mail.py`（成熟版） | **IMAP 枚举全部文件夹**：`\Inbox \Junk \Spam…` + 中文"垃圾箱/收件箱"；Graph 的 inbox+junkemail；每 35s 触发重发 | **多箱扫描**是真实邮箱的正解——建议借鉴 |
| `grok-pure/email_service.py` | 8 种邮箱源（mailtm/gptmail/fce/tmail/luckmail/mailnest/outlook/gmail） | LuckMail 等服务商直接返回 `verification_code` 字段 |
| AutoJs6 临时邮箱版 | 页面内直调 DuckMail API，2s×48 | 无文件桥（页面内自取） |

**启示**（真实邮箱的判定会波动）：2026-09-26 13:36 实测有一封验证码直接进了**收件箱**而非垃圾箱，
守望只看 Junk 会漏收。成熟项目（outlook_mail.py）的做法就是"收件箱 + 垃圾箱都扫"。

**本项目当前决策（2026-09-26 定）**：保持**只扫垃圾箱**，用"服务端归一 + 客户端归位"兜住漂移，
而不是放宽守望的扫描范围：

1. **根治（服务端）**：QQ 网页端设收信规则/黑名单 —— 发件人包含 `x.ai`（信封域是 SRS 重写后的
   `em7846.x.ai`，只设 `noreply@x.ai` 可能匹配不上）→ 移动到垃圾箱。
2. **兜底（客户端）**：`~/bin/grok-mail-to-junk.py --loop` 常驻，每 5 秒扫收件箱最近 30 封，
   把 from x.ai 的邮件 `UID COPY` 到 Junk 再删原件 → 落箱到进垃圾箱 ≤5 秒，守望始终只认垃圾箱。

取舍：守望保持最简（单箱、快、逻辑少）；归位有最长几秒的客户端延迟；要零延迟就靠第 1 条。
另外实测：QQ 的"其他文件夹"是**只读箱**（`IMAP4.readonly`），服务端不允许搬信，归位脚本需跳过它。
